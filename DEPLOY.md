# Как развернуть «Живая ленту» 5.1.2 на любом Ubuntu-сервере

Два файла в папке `dist/`:

| Файл | Размер | Что это |
|---|---|---|
| `livefeed-5.1.2-source.tar.gz` | 210 КБ | Код приложения, скрипты установки и проверки |
| `livefeed-5.1.2-images.tar.gz` | 84 МБ | Готовые образы Docker: приложение и nginx |
| `SHA256SUMS.txt` | 400 Б | Контрольные суммы, сверять после копирования |

С ними сервер поднимается **без доступа в интернет**: код на месте, образы
приезжают в архиве, снаружи ставить нечего, кроме Docker.

Комплект лежит на машине разработчика в `dist/`, и его достаточно для любого
сервера — Docker на этой машине не нужен. Архив образов при этом проверяется
загрузкой: `docker load -i livefeed-5.1.2-images.tar.gz` обязан напечатать
`Loaded image: livefeed:5.1.2` и `Loaded image: nginx:1.27-alpine`.

---

## Коротко, если всё понятно

```bash
# 1. На своей машине положить оба файла на сервер
scp dist/livefeed-5.1.2-source.tar.gz dist/livefeed-5.1.2-images.tar.gz root@АДРЕС:/tmp/

# 2. На сервере
ssh root@АДРЕС
cd /tmp
tar -xzf livefeed-5.1.2-source.tar.gz -C /tmp/lf
ADMIN_PASSWORD=ВАШ_ПАРОЛЬ bash /tmp/lf/deploy.sh

# 3. Открыть http://АДРЕС/admin и войти паролем
```

Скрипт сам поставит Docker, откроет порты, разложит код, поднимет контейнеры
и напечатает адрес и пароль в конце.

---

## Что нужно от сервера

- Ubuntu 22.04 или новее (проверено на 26.04 LTS), архитектура x86-64
- root по SSH
- 512 МБ свободной памяти и 2 ГБ на диске — этого хватает с запасом
- **Порты 80 и 443 должны быть открыты** наружу: в самом `ufw` и, если есть,
  в Security Group / firewall панели хостера

Домен не обязателен. Без него сайт работает по адресу `http://АДРЕС`, но пароль
тогда идёт открытым текстом — это годится для проверки, но не для мероприятия
с гостями (см. раздел «Про https»).

## Подробно, шаг за шагом

### Шаг 1. Положить файлы на сервер

```bash
scp dist/livefeed-5.1.2-source.tar.gz dist/livefeed-5.1.2-images.tar.gz root@АДРЕС:/tmp/
scp "C:\Users\9900x\.ssh\livefeed_deploy" root@АДРЕС:~/.ssh/authorized_keys   # необязательно
```

### Шаг 2. Запустить установку

```bash
ssh root@АДРЕС
cd /tmp
tar -xzf livefeed-5.1.2-source.tar.gz -C /tmp/lf
cp livefeed-5.1.2-images.tar.gz /tmp/lf/          # чтобы образ достался без сети
ADMIN_PASSWORD=ВАШ_ПАРОЛЬ bash /tmp/lf/deploy.sh
```

Если пароль не задавать, скрипт сгенерирует случайный и напечатает его.

Скрипт идёт по шагам: ставит Docker → открывает порты → кладёт образ →
разворачивает код в `/opt/livefeed` → готовит `.env` → поднимает контейнеры →
ждёт ответа и печатает адрес.

**Повторный запуск безопасен.** `.env` с паролем не перезаписывается, данные
(события, фотографии, заставки) не трогаются. На новую версию — тот же архив,
та же команда.

### Шаг 3. Убедиться, что всё поднялось

```bash
curl http://АДРЕС/api/health          # {"ok":true,"events":0}
cd /opt/livefeed && docker compose ps # оба контейнера Up
```

### Шаг 4. Завести событие

Открыть `http://АДРЕС/admin`, войти паролем админа, создать событие с паролем
ведущего. В карточке события появятся три ссылки и QR:

| Ссылка | Кому | Пароль |
|---|---|---|
| Модераторская | ведущему на ноутбуке | пароль события |
| Экранная | на проектор | без пароля |
| Гостям | распечатать рядом с QR | без пароля, с кодом внутри |

## Проверка, что развёрнутое работает

Всё в одной команде — она сама кладёт файлы в контейнер, передаёт каждому
набору нужный адрес и убирает за собой:

```bash
cd /opt/livefeed && bash verify.sh
```

Ожидаемый вид:

```
==> Наборы
    сценарий снаружи       OK=47  FAIL=0
    заставка               OK=29  FAIL=0
    события                OK=84  FAIL=0
    сценарии HTTP          OK=56  FAIL=0
    админ-панель           OK=24  FAIL=0
    пределы показа         OK=25  FAIL=0
    слайдшоу               OK=91  FAIL=0
    показ в реальном       OK=24  FAIL=0
    без модерации          OK=45  FAIL=0
    миграции базы          OK=14  FAIL=0
    сети прокси            OK=18  FAIL=0
    ворота сертификата     OK=18  FAIL=0
    сессии                 OK=24  FAIL=0
    ввод кода              OK=27  FAIL=0
    скрипты страниц        OK=181 FAIL=0
==> Статика и разметка
    аудит статики          OK=31  FAIL=0
==> Комплект развёртывания
    комплект развёртывания OK=35  FAIL=0

Итог: проверок пройдено 773, провалено 0.
```

**Набор, отчитавшийся `OK=0`, — это провал, а не успех.** Раньше он выглядел
как «проверять было нечего», и сервер рапортовал «провалов нет» при двух
наборах, не выполнивших ни одной проверки: оба лежат в `/tmp` и делают
`from app import config`, а python кладёт в `sys.path` каталог **скрипта**,
а не рабочий, так что `-w /app` не помогает — нужен `PYTHONPATH=/app`.
Теперь `verify.sh` считает нулевой набор провалом, печатает хвост его вывода
и перечисляет такие наборы в конце. Если они в списке — причина в выводе
выше.

Живой сценарий (`check_remote.py`) идёт снаружи, через nginx. Из контейнера
такой адрес виден не всегда: нестандартный опубликованный порт или сервер за
NAT без обратной переадресации соединение не пропускают. `verify.sh` в этом
случае переключается на внутренний адрес приложения и **явно пишет**, что путь
через nginx в этом прогоне не проверен, — чтобы это не выглядело как «всё хорошо».

Остальные наборы всегда бьют в `http://127.0.0.1:8000` — это адрес приложения
внутри сети контейнеров, он верный всегда.

Задать адрес вручную:

```bash
VERIFY_HOST=10.0.0.5 bash verify.sh
```

Если сервер за NAT, проверку через nginx проще сделать с машины, откуда он
доступен, — с публичным адресом и снаружи:

```bash
python deploy/check_remote.py http://ВАШ_АДРЕС
```

Отдельный набор, если нужно глянуть прицельно:

```bash
cd /opt/livefeed
docker cp test_splash.py live-feed-app:/tmp/
docker exec -e ADMIN_PASSWORD=ПАРОЛЬ live-feed-app \
    python /tmp/test_splash.py http://127.0.0.1:8000
docker exec -u root live-feed-app rm -f /tmp/test_splash.py
```

Адрес `http://127.0.0.1:8000` обязателен: по умолчанию наборы бьют в
`127.0.0.1:8123`, а такого порта на сервере нет. Проверка скриптов страниц
ищет каталог `static/` рядом с собой, поэтому её запускают с каталогом `/app`:

```bash
docker cp test_frontend.py live-feed-app:/app/
docker exec -w /app live-feed-app python /app/test_frontend.py
```

Проверки убирают за собой заведённые события. Если прогон оборвался на середине
и остался мусор — удалить можно вручную: папкой в томе `livefeed_app-data` или
через админку, кнопка удаления.

Полный прогон — 773 проверки за один заход, это заметная нагрузка на машину с
1 ГБ памяти. Если сервер слабый, запускайте наборы по одному (команда выше).

## Управление

```bash
cd /opt/livefeed

docker compose ps                # состояние
docker compose logs -f nginx     # журналы (доступ наружу — nginx)
docker compose logs -f app       # журналы приложения
docker compose restart           # перезапуск
docker compose down              # остановить
docker compose up -d             # поднять обратно
```

### Обновить на новую версию

```bash
scp НОВЫЙ/livefeed-5.1.2-source.tar.gz root@АДРЕС:/tmp/
scp НОВЫЙ/livefeed-5.1.2-images.tar.gz root@АДРЕС:/tmp/

ssh root@АДРЕС
rm -rf /tmp/lf && tar -xzf /tmp/livefeed-5.1.2-source.tar.gz -C /tmp/lf
cp /tmp/livefeed-5.1.2-images.tar.gz /tmp/lf/
ADMIN_PASSWORD=СТАРЫЙ_ПАРОЛЬ bash /tmp/lf/deploy.sh
```

События, фотографии и заставки переживают обновление — они в томе Docker, а не в коде.

### Откатиться на прошлую версию

```bash
cd /opt/livefeed
sed -i 's|image: livefeed:5.1.2|image: livefeed:5.0|' docker-compose.yml
docker compose up -d
```

Образы прошлых версий можно оставить заранее:
`docker tag livefeed:5.0 livefeed:5.0-prev` — **до** развёртывания новой, иначе
метка переедет на новый образ и откатываться будет нечем. Готовый бэкап с
данными и прежним образом лежит на сервере: `/root/backup-*/RESTORE.txt`.

### Развернуть с машины, где нет Docker

Так комплект и задуман: архив образов не требует Docker **на той машине,
откуда его копируют**. Нужен только `scp`.

```powershell
# на своей машине — архивы уже собраны в dist/
python verify_kit.py        # проверить, что комплект целый
scp dist/livefeed-5.1.2-images.tar.gz dist/livefeed-5.1.2-source.tar.gz root@АДРЕС:/tmp/
```

На сервере разворачивается как обычно, тремя строками из раздела «Коротко».

`verify_kit.py` проверяет то, что можно проверить без Docker: целостность
gzip, состав архива, что в манифесте лежат именно `livefeed:5.1.2` и
`nginx:1.27-alpine` (и **нет** старой версии — иначе на другой машине
развернётся не то), что в образе задан пользователь `livefeed` и прописано
хранилище `/app/data`, и что в исходниках нет CRLF.

Контрольную сумму после копирования можно сверить на любой машине с Python —
ожидаемые значения лежат в `SHA256SUMS.txt`:

```bash
python -c "import hashlib,sys;print(hashlib.sha256(open(sys.argv[1],'rb').read()).hexdigest())" livefeed-5.1.2-images.tar.gz
```

Если файл переписывали через сеть, сходиться будет именно с `SHA256SUMS.txt`,
а не с тем, что напечатано в этом файле: сам `DEPLOY.md` входит в архив
исходников, поэтому упоминающая его сумма была бы саморазрушающейся.

### Перенести на другой сервер

Данные лежат в томе Docker. Скопировать можно так:

```bash
# на старом
docker run --rm -v livefeed_app-data:/data -v "$PWD":/backup \
    alpine tar czf /backup/livefeed-data.tar.gz -C /data .
scp livefeed-data.tar.gz root@НОВЫЙ:/tmp/

# на новом — сначала развернуть, потом:
cd /opt/livefeed
docker compose down
docker run --rm -v livefeed_app-data:/data -v /tmp:/backup \
    alpine sh -c "cd /data && tar xzf /backup/livefeed-data.tar.gz"
docker compose up -d
```

### Резервная копия данных

```bash
cd /opt/livefeed
docker run --rm -v livefeed_app-data:/data -v "$PWD":/backup \
    alpine tar czf /backup/livefeed-data-$(date +%F).tar.gz -C /data .
```

Снимок тома можно и на ходу (`docker commit` не нужен, достаточно короткой
остановки), но проще делать копию, когда никто не пишет.

## Про https

Без домена сертификат выпустить не на что, и сайт живёт по http.

С доменом всё включается само: впишите в `/opt/livefeed/.env`

```
DOMAIN=ваш-домен.ru
ACME_EMAIL=почта@ваш-домен.ru
```

и выполните

```bash
cd /opt/livefeed && docker compose up -d
```

Домен должен уже указывать на этот сервер. Контейнер nginx сам поставит
acme.sh, получит сертификат Let's Encrypt, будет следить за его обновлением и
переводить http на https. Затем `FORCE_HTTPS=true` (уже включено по умолчанию)
начнёт ставить флаг Secure на cookie.

## Если что-то пошло не так

**Сайт не открывается снаружи.**

```bash
curl http://127.0.0.1/api/health      # отвечает?
```

Отвечает, а снаружи нет — закрыт порт. Проверьте `ufw status` и Security Group
в панели хостера. Это самая частая причина.

**Контейнер перезапускается по кругу.**

```bash
docker compose logs --tail=50 app
```

Обычно это `.env` без `ADMIN_PASSWORD` — приложение не стартует и падает.

**«Не удалось войти в админку».**

Пароль админа лежит в `/opt/livefeed/.env`. Посмотреть и сменить:

```bash
grep ADMIN_PASSWORD /opt/livefeed/.env
sed -i 's|^ADMIN_PASSWORD=.*|ADMIN_PASSWORD=НОВЫЙ_ПАРОЛЬ|' /opt/livefeed/.env
docker compose up -d --force-recreate
```

**Гость не может отправить фото.**

Смотрите `/opt/livefeed/data` — точнее, том. Проверьте свободное место:
`df -h /`. Загрузки не умеют делить один диск бесконечно.

**Заставка не появляется на экране.**

Кнопка «Заставка» в панели ведущего должна быть нажата, картинка — загружена
в блоке внизу той же панели. Состояние видно в ответе:
`curl http://127.0.0.1:8000/api/health` не показывает, нужно смотреть
`/e/<событие>/api/moderator/state` ведущим.

## Что где лежит на сервере

```
/opt/livefeed/
  app/  static/  deploy/        код
  deploy.sh                      установщик
  verify.sh                      прогон всех проверок
  test_*.py  check_release.sh    сами проверки
  docker-compose.yml  Dockerfile
  .env                           пароль админа и настройки (chmod 600)

томы Docker:
  livefeed_app-data              /app/data — вот это НЕ трогать при обновлении
    events/<событие>/
      config.json                коды, пароли, интервал
      app.db                     сообщения
      uploads/                   фотографии
      splash.jpg                 заставка события
  livefeed_certs                 сертификаты Let's Encrypt
  livefeed_acme-www              проверка домена при выпуске сертификата
```

Показ идёт по адресу `http://АДРЕС/admin`, корневой `/` перенаправляет туда же.
