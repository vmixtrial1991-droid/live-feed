# Развёртывание на VPS

Скрипты ставят nginx, сертификат (если есть домен), python-окружение и сервис systemd.
Работают на чистом Ubuntu 22.04/24.04, Debian 12, Ubuntu 24.04 с OpenSSH 9.6.

## Две команды

**С доменом** — https и сертификат Let's Encrypt:

```
ssh root@IP 'bash -s' ваш-домен.ru < deploy/remote.sh
```

**По IP, без домена** — для теста, только http:

```
ssh root@IP 'bash -s' < deploy/remote-ip.sh
```

Оба вызывают `install.sh`, ставят всё сами и узнают адрес автоматически. Повторный
запуск безопасен: пароль модератора сохраняется, база и фото не затираются.

Если файлы уже лежат на сервере:

```
scp -r app static deploy run.py requirements.txt root@IP:/tmp/livefeed
ssh root@IP 'bash /tmp/livefeed/deploy/install.sh ваш-домен.ru /tmp/livefeed'
```

Почта для Let's Encrypt задаётся переменной, иначе подставится `admin@ваш-домен`:

```
ssh root@IP "ACME_EMAIL=почта@домен.ru bash -s" ваш-домен.ru < deploy/remote.sh
```

## Что нужно до запуска

1. **Домен с A-записью на IP сервера** — только для варианта с https. Без него
   Let's Encrypt не выдаст сертификат, а QR-код гостям будет бесполезен.
2. **Порты 80 и 443 открыты наружу** — в firewall и в панели провайдера. Порт 8000
   открывать не нужно: nginx обращается к приложению локально.
3. **Учётка с sudo** либо root.
4. **Python 3.11+** на сервере.

## Что уезжает на сервер

| Место | Назначение |
|---|---|
| `/opt/live-feed` | код и виртуальное окружение |
| `/opt/live-feed/data` | пароль администратора и папки всех событий |
| `/opt/live-feed/data/events/АДРЕС` | база, фото и настройки одного события |
| `/etc/live-feed.env` | пароль и публичные настройки, права `640 root:livefeed` |
| `/etc/systemd/system/live-feed.service` | автозапуск и перезапуск при падении |
| `/etc/nginx/sites-available/live-feed` | прокси с TLS и пробросом WebSocket |

Приложение слушает только `127.0.0.1:8000` и напрямую из интернета недоступно.

Резервная копия — это папка `data`: в ней лежат все события разом.

```
sudo systemctl stop live-feed
sudo tar czf /root/live-feed-$(date +%F).tgz -C /opt/live-feed data
sudo systemctl start live-feed
```

## Файлы в deploy/

| Файл | Назначение |
|---|---|
| `remote.sh` | установка с доменом через ssh-пайп |
| `remote-ip.sh` | установка без домена, сама узнаёт адрес сервера |
| `install.sh` | основной скрипт, оба вызывают его |
| `live-feed.env.example` | образец настроек; на сервере станет `/etc/live-feed.env` |
| `live-feed.service` | юнит systemd |
| `nginx.conf` | прокси с TLS |
| `nginx-http.conf` | прокси без TLS, для варианта по IP |
| `nginx-websocket.conf` | фрагмент `map` для WebSocket, кладётся в `conf.d/` |
| `docker/` | конфигурация nginx и выпуск сертификата для варианта с Docker |
| `check_remote.py` | проверка развёрнутого сервера, см. ниже |

## Переменные окружения

Читаются из `/etc/live-feed.env`.

| Переменная | Зачем |
|---|---|
| `ADMIN_PASSWORD` | пароль входа в админку; при первом старте генерируется |
| `PUBLIC_BASE_URL` | адрес для QR-кода и ссылок на события |
| `TRUSTED_PROXIES` | адреса, чьим `X-Forwarded-For` можно верить; здесь сам nginx |
| `FORCE_HTTPS` | редирект `http` → `https` |
| `COOKIE_SECURE` | флаг `Secure` на cookie |
| `TRUSTED_HOSTS` | допустимые домены; чужой `Host` получает 400 |

Заголовок и подпись события задаются в самом событии, а не в окружении: они живут в
`data/events/АДРЕС/config.json` и меняются из админки.

Пароль ведущего — свой у каждого события, задаётся в админке при создании.

Смена пароля администратора:

```
sudo nano /etc/live-feed.env
sudo systemctl restart live-feed
```

## Проверка развёрнутого сервера

Скрипт запускается на самом VPS и проверяет всё через nginx, как это видят гости:

```
/opt/live-feed/venv/bin/pip install websockets
scp -i ключ deploy/check_remote.py root@IP:/opt/livefeed/
ssh root@IP 'cd /opt/livefeed && ./venv/bin/python check_remote.py http://IP'
```

Скрипт входит в админку, заводит **временное событие**, работает уже по нему и в конце
удаляет его. В ленте ничего не остаётся.

Покрыто: страницы события, разграничение доступа, регистрация по коду приглашения, вход
ведущего, доставка по WebSocket четырём подписчикам сразу, порядок показа, отметки
«показано», QR на экране, загрузка и сжатие фото, правка и удаление, автопрокрутка.

Режим с доменом и прокси-заголовками проверяется отдельно, локально:

```
TRUSTED_PROXIES=127.0.0.1,::1 FORCE_HTTPS=true COOKIE_SECURE=true \
TRUSTED_HOSTS=example.com LF_DATA_DIR=data-proxy python run.py --port 8124

LF_DATA_DIR=data-proxy LF_TEST_ROOT=http://127.0.0.1:8124 \
LF_TEST_HOST=example.com python test_proxy.py
```

## Режим без домена

Работает по http, поэтому пароль ведущего и пароль администратора идут открытым текстом.
Из защит остаётся только лимит на вход. Для теста приемлемо, для настоящего мероприятия
в публичном интернете нужен домен и вариант с сертификатом.

## Обслуживание

```
sudo systemctl status live-feed      # состояние
sudo systemctl restart live-feed     # перезапуск
sudo journalctl -u live-feed -f      # логи
```

### После обновления кода

Страницы ссылаются на скрипты с отметкой версии, поэтому после обновления
браузер сам приходит за новыми файлами. Но **уже открытые вкладки и
страницы на телефонах продолжают работать со старым кодом** — их нужно
перезагрузить вручную.

Признак, что вкладка осталась со старой версией: в логах nginx видны
запросы на адреса без префикса `/e/АДРЕС/`, например `GET /ws/display`,
и ответы 403 или 404 на них. Скажите гостям закрыть страницу и открыть
заново по QR-коду.

Обновление на Docker:

```
cd /opt/livefeed
docker compose up -d --build --force-recreate
```

Бэкап: том `app-data` содержит все события разом.

Список событий можно посмотреть и вручную — это просто папки:

```
ls /opt/live-feed/data/events/
```

Событие удаляется либо из админки, либо удалением его папки. Во втором случае соединения
открытых экранов останутся висеть до перезапуска сервиса, так что лучше через админку.

## Чего установка не делает

- Не открывает порты в firewall. Если `apt` или выпуск сертификата не прошли, проверьте
  `ufw status` и панель провайдера.
- Не настраивает бэкапы по расписанию. Команда выше — разовая.
- Не ставит fail2ban. Лимит входа достаточно защищает страницы входа, но ssh-порт
  лучше оставить стандартным и с ключами, а не с паролем.
- Не публикует проект в интернет. Репозиторий живёт только на вашей машине.
