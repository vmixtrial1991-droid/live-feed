# Живая лента 3.7 — несколько событий на одном сервере

Веб-приложение для мероприятий: гости по QR-коду вводят имя и отправляют текст или фото, и всё
сразу появляется на общей витрине и на полноэкранном показе. Модерации нет — сообщение уходит
в эфир в момент отправки.

Главное отличие от самой первой версии: **событий сколько угодно**. Заводите событие в админке —
появляются свои три ссылки и свой QR-код для гостей. Дальше всё работает само, без вас.
Два события могут идти одновременно и не видят сообщений друг друга. После события его можно
удалить, и от него ничего не останется.

Что нового в 3.7:

- **Экран поделил высоту на постоянные доли.** Раньше фото получало «сколько осталось» после текста,
  и кадр от слайда к слайду прыгал. Теперь высота зоны делится заранее: подпись отправителя
  занимает ровно 6 %, фото, когда оно идёт с текстом, — ровно 64 %, а всё остальное достаётся
  тексту, и он под это место подстраивается. Соотношение одно на любом экране: от проектора
  640×480 до 4K.
- **Текст больше не режется.** Нашёл и починил три обрезания, которые показывались только на
  части экранов: строка была чуть короче самих букв и срезала низ символов с выносными
  элементами; «влезает ли текст» определялось по высоте блока, а обрезает его фактическая
  высота содержимого; подгонка заканчивалась на размере шрифта, который ещё не был проверен,
  и у границы раскачивалась между двумя соседними.
- **Длинное имя не уезжает вбок.** Подпись раньше брала ширину по содержимому, и длинное имя
  могло вылезти за кадр в сторону. Теперь она по ширине зоны, переносится и занимает свои 6 %.

Что было в 3.6:

- **Текст не длиннее 56 символов.** Столько реально читается с последнего ряда. Гость видит
  счётчик и предупреждение заранее; сервер длинный текст не обрезает молча, а отказывает
  и объясняет, на сколько сократить. Предел меняется переменной `LF_MAX_TEXT_LEN`.
- **Короткий текст на экране крупнеет.** «Да!» больше не висит строчкой на стене: кегль
  подбирается под свободное место.
- **Маленькие фото увеличиваются.** Гость прислал скриншот или кадр с телефона — на проекторе
  он был точкой. Теперь такое фото растягивается до трёхкратного размера, но не больше
  свободного места и не выходя за безопасную зону кадра.
- **Вёрстка не зависит от разрешения.** Проверено на одиннадцати — от проектора 4:3
  640×480 до 4K: ничего не вылезает за кадр, строки не режутся, фото не искажается.
- **Кнопка «Отправить»** вместо «Отправить на модерацию»: модерации нет уже давно, и надпись
  обещала то, чего не происходит.

Что было в 3.5: **заставка на весь экран**. Ведущий грузит картинку один раз внизу своей
панели, дальше жмёт кнопку «Заставка» — она плавно закрывает экран, повторное нажатие так же
плавно убирает её и возвращает показ отправленного. Без картинки будет просто название события.

# Быстрый старт

## Вариант 1: Docker (рекомендую)

Работает везде, где есть Docker. Ничего не ставится в систему, обновляется одной командой.

```bash
git clone <адрес-репозитория> live-feed && cd live-feed
cp .env.example .env
nano .env                    # вписать ADMIN_PASSWORD и, если есть, DOMAIN
docker compose up -d
```

Откройте `/admin` — там создаются события. Пароль администратора — тот, что в `.env`.

Сертификат выпускается сам, если `DOMAIN` в `.env` указывает на ваш сервер. Пока сертификата
нет, сайт работает по http как обычный сайт, и редирект на https не включается — иначе без
сертификата посетителя уводило бы в никуда. Как только сертификат появится, https заработает
сам, перезапускать контейнер не нужно.

Обновление:

```bash
git pull && docker compose up -d --build
```

Резервная копия: том `app-data` — это и есть все события.

## Вариант 2: без Docker

Для Ubuntu 22.04/24.04 и Debian 12, где apt и systemd на месте.

По IP, для теста, только http:

```bash
git clone <адрес-репозитория> live-feed && cd live-feed
sudo bash deploy/remote-ip.sh
```

С доменом, с сертификатом Let's Encrypt:

```bash
git clone <адрес-репозитория> live-feed && cd live-feed
sudo bash deploy/remote.sh ваш-домен.ru
```

Оба скрипта ставят nginx, окружение и сервис systemd, сами узнают адрес сервера. Пароль
администратора печатается в конце и сохраняется в `/etc/live-feed.env`. Повторный запуск
безопасен: пароль сохраняется, события не затираются.

Подробности, состав файлов и обслуживание — в [deploy/README.md](deploy/README.md).

## Локально, без сервера

```bash
python -m pip install -r requirements.txt
python run.py
```

После старта в консоли появятся адрес и пароль администратора:

```
┌──────────────────────────────────────────────────────────────┐
│  Живая лента — события
│
│  Админка:            http://192.168.31.251:8000/admin
│  Пароль админа:      XXXXXXXXXXXX
│
│  Событие заводится в админке: там появятся три ссылки —
│  для ведущего, для экрана и для гостей с QR-кодом.
```

## Что нужно до развёртывания

1. **VPS** с Ubuntu 22.04/24.04 или Debian 12. Подойдёт сама дешёвая машина: 512 МБ RAM
   и 10 ГБ диска хватает. Проверено на 1 ГБ RAM.
2. **Порты 80 и 443** открыты наружу — в firewall провайдера и в самой системе.
   Порт 8000 открывать не нужно.
3. **Домен** с A-записью на IP сервера — только если хотите https. Без него сайт работает
   по http, и пароль ведущего передаётся открытым текстом.
4. **Доступ по ssh с правом sudo** либо под root.

# Как это устроено

## Админка

`/admin` — одна страница, где заводятся события.

- **Новое событие**: название, подпись, необязательный пароль ведущего и необязательный
  адрес в ссылках. Название переводится в латиницу автоматически: «Свадьба Маши и Саши» →
  `svadba-mashi-i-sashi`. Если адрес занят, добавится `-2`.
- **Карточка события**: QR-код для гостей, три готовые ссылки и кнопки «копировать».
  Здесь же меняются название, пароль ведущего и код приглашения.
- **Удаление**: уносит сообщения, фотографии и участников, отключает экраны. Отменить нельзя,
  поэтому спрашиваем дважды.

Пароль администратора один на сервер. Пароль ведущего — свой у каждого события; если оставить
пустым, ведущий не сможет войти, пока не задаст пароль в карточке события.

## Адреса

У каждого события свой адрес, и всё живёт под ним:

| Адрес | Кто открывает | Что делает |
|---|---|---|
| `/admin` | администратор | список событий, создание, удаление |
| `/e/АДРЕС/` | все гости, экран в зале | витрина всех сообщений этого события |
| `/e/АДРЕС/send` | гости | отправка текста и фото, видно свои отправки |
| `/e/АДРЕС/screen` | проектор | полноэкранный показ: одно сообщение за раз |
| `/e/АДРЕС/join?t=КОД` | гости по QR | ввод имени, дальше сессия живёт 90 дней |
| `/e/АДРЕС/moderator` | ведущий | управление показом, список пришедшего, QR |

Три ссылки, которые вы отдаёте организатору события:

1. **Ведущему** — `/e/АДРЕС/moderator`, вход по паролю события.
2. **Экрану** — `/e/АДРЕС/screen`, без пароля.
3. **Гостям** — `/e/АДРЕС/join?t=КОД`, это и есть QR-код, без пароля.

## Почему события не пересекаются

Событие — это просто папка:

```
data/
  config.json              пароль администратора
  events/
    svadba-mashi-i-sashi/
      config.json          название, код приглашения, пароль ведущего
      app.db               сообщения и участники этого события
      uploads/             фотографии этого события
    korporativ-2026/
      ...
```

Отдельного реестра событий нет, и он не нужен: список событий — это содержимое `data/events`.
Отсюда два следствия:

- **Удаление не оставляет хвостов.** Удалили папку — исчезло всё: база, фотографии, настройки.
  Нечего отдельно чистить реестр, потому что его не существует.
- **События не видят друг друга.** У них физически разные базы и разные папки с фотографиями.
  Плюс у каждого свои cookie: имя участника и имя ведущего включают адрес события, поэтому
  вход в одно событие не даёт доступа к другому. В одном браузере можно участвовать в двух
  ивентах сразу — они не затирают друг друга.

## Как проходит мероприятие

1. Ведущий открывает `/e/АДРЕС/moderator` и входит по паролю события.
2. На экране он жмёт **QR на экране** — код появляется поверх сообщений, и показ на время
   останавливается, чтобы гости спокойно сканировали.
3. Гость сканирует камерой телефона, вводит имя. Cookie сохраняется на 90 дней.
4. Гость пишет текст и прикладывает фото. Сообщение **сразу** появляется на витрине и встаёт
   в конец очереди показа — ждать проверки не нужно.
5. Сверху панель управления: **Назад**, **Пауза/Продолжить**, **Вперёд** и ползунок
   длительности показа от 3 до 120 секунд.
6. Ниже полоса «Сейчас на экране» и список пришедшего. Уже показанные сообщения приглушены
   и помечены «показано», не показанные — подсвечены и помечены «новое». Когда показ проходит
   полный круг, отметки сбрасываются.
7. У любого сообщения: **▶** показать сейчас, **↑ ↓ ⤒** двигать по очереди, **✎** поправить
   текст, **✕** удалить. **Заново** начинает круг заново.

## Горячие клавиши в кабинете

| Клавиша | Действие |
|---|---|
| `Пробел` | пауза / продолжить |
| `←` `→` | листать слайды |
| `Q` (рус. `Й`) | показать или скрыть QR на экране |

На странице `/e/АДРЕС/screen` работают `←` `→` `Пробел`, но только если с этой вкладки выполнен
вход ведущим (страница сама это проверяет). Клик по экрану включает полноэкранный режим.

## Что под капотом

- **FastAPI + uvicorn**, WebSocket для реального времени, задержка от появления сообщения до
  экрана — десятки миллисекунд.
- **SQLite** — отдельный файл на событие, фото рядом в `uploads/`.
- **Pillow** сжимает фото на сервере: не длиннее 1600 px, JPEG качества 82, EXIF-поворот
  учитывается, прозрачность заливается белым. PNG на 5 МБ обычно становится 60–150 КБ.
- Пароль администратора и пароль ведущего хранятся как PBKDF2-хеш, сравнение — constant-time.
  Есть защита от перебора: 8 попыток за 5 минут с одного адреса, счётчики в SQLite.
- Cookie подписаны HMAC и привязаны к назначению. Нарисовать cookie в браузере не получится —
  в прошлой версии это было возможно.
- Сессия гостя — httpOnly cookie на 90 дней, имя включает адрес события.
- Показ живёт на сервере, поэтому все проекторы одного события показывают одно и то же.
  Переключение слайдов крутит один общий цикл, а не задача на каждое событие.
- Показ ходит по кругу: прошёл весь список — начинает заново, отметки «показано» сбрасываются.

## Настройка

### Через окружение (рекомендую)

При Docker это файл `.env`, при запуске без Docker — переменные окружения или
`/etc/live-feed.env`. Полный список с комментариями — в [.env.example](.env.example).

| Переменная | Смысл |
|---|---|
| `ADMIN_PASSWORD` | пароль входа в админку |
| `DOMAIN`, `ACME_EMAIL` | домен для сертификата и почта (только для Docker) |
| `PUBLIC_BASE_URL` | адрес для QR-кода, если сервер за прокси с другим именем |
| `TRUSTED_PROXIES` | адреса и подсети, чьим `X-Forwarded-For` можно верить |
| `FORCE_HTTPS` | редирект `http` → `https` |
| `COOKIE_SECURE` | флаг `Secure` на cookie |
| `TRUSTED_HOSTS` | допустимые домены; чужой `Host` получает 400 |
| `CERT_FILE` | файл сертификата: пока его нет, https выключен |

`TRUSTED_PROXIES` принимает и точные адреса, и подсети в CIDR. За Docker адрес прокси меняется
при каждом пересоздании, поэтому в `.env.example` прописаны сети частных адресов.

### В файле

Настройки события — в `data/events/АДРЕС/config.json`: название, подпись, код приглашения,
пароль ведущего, интервал показа. Пароль администратора — в `data/config.json`.

## Проверка

Тесты запускаются против работающего сервера. Каждый набор заводит своё событие и убирает
его за собой:

```
python -m pip install -r requirements.txt websockets
python run.py --port 8123

python check_admin_page.py       # админка: страницы, создание, QR, удаление
python test_events.py            # события: изоляция, доступ, удаление
python test_api.py               # сценарии через HTTP
python test_realtime.py          # WebSocket: доставка, права, автопрокрутка
python test_no_moderation.py     # режим без модерации целиком
```

Три теста работают без сервера:

```
python test_proxy_networks.py    # доверие прокси по подсетям
python test_migration.py         # обновление базы прошлой версии
python test_cert_gate.py         # включение https только с сертификатом
python test_frontend.py          # скрипты страниц: синтаксис и ссылки на файлы
```

`test_events.py` — главный для 3.0. Он проверяет то, ради чего всё затевалось: два события
не видят сообщений друг друга, у каждого свой код приглашения и свой пароль ведущего, вход
в кабинет одного события не открывает другой, нарисованная вручную cookie не пускает, а после
удаления от события не остаётся ни файлов, ни страниц.

`test_api.py` покрывает страницы и редиректы, регистрацию по QR, отказ по чужому коду,
загрузку текста и фото, сжатие, попадание в эфир сразу, права кабинета, порядок показа,
управление экраном, отметки «показано», правку текста и имени, удаление вместе с файлом,
обход каталога фотографий, смену кода приглашения.

`test_no_moderation.py` проверяет, что модерации действительно нет: эндпоинт одобрения
не существует, отправка сразу видна всем, в состоянии кабинета нет очереди и отклонённых.

`test_realtime.py` покрывает то, чего не видно в HTTP-тесте: гость не попадает в
`/ws/moderator` и `/ws/participant`, отправка без всякой проверки доезжает до всех экранов
сразу, автор видит подтверждение, перестановки не ломают порядок, отметки «показано»
проставляются и сбрасываются, QR останавливает прокрутку, слайды меняются по таймеру.

`test_proxy.py` проверяет режим за nginx: редирект на https, флаги cookie, отказ на чужой
`Host`, лимит входа по реальному адресу. Запускается с переменными окружения:

```
TRUSTED_PROXIES=127.0.0.1,::1 FORCE_HTTPS=true COOKIE_SECURE=true \
TRUSTED_HOSTS=example.com LF_DATA_DIR=data-proxy python run.py --port 8124

LF_DATA_DIR=data-proxy LF_TEST_ROOT=http://127.0.0.1:8124 \
LF_TEST_HOST=example.com python test_proxy.py
```

Проверка развёрнутого сервера — одним файлом, запускается на самом VPS и смотрит
на сайт снаружи, через nginx:

```
/opt/live-feed/venv/bin/pip install websockets
scp -i ключ deploy/check_remote.py root@IP:/opt/livefeed/
ssh root@IP 'cd /opt/livefeed && ./venv/bin/python check_remote.py https://ваш-домен'
```

В CI те же проверки идут на Python 3.11 и 3.12, плюс `shellcheck` для скриптов установки и
сборка образа — см. [.github/workflows/tests.yml](.github/workflows/tests.yml).

## Ограничения

- Модерации нет, поэтому если кто-то пришлёт неуместное, останется в эфире. Спасают
  кнопка **✕** и порядок показа — но до неё дойдёт дело в зале.
- Антиспам-слов нет: любой, у кого есть ссылка-приглашение, может писать.
- Рассчитано на одного администратора.
- Резервных копий по расписанию нет. Для событий с историей сохраняйте папку `data/`
  или том `app-data`.
- SQLite и файлы на локальном диске: два инстанса приложения не будут видеть общие данные,
  поэтому масштабировать можно только вертикально.
- Старые адреса (`/`, `/screen`, `/moderator`) в 3.0 не работают: `/` открывает админку.
  Если переносите данные с 2.0, их нужно залить заново — автоматического переноса нет.

## Переход с 2.0 на 3.0

Данные не переносятся автоматически: в 2.0 был один набор сообщений на сервер, в 3.0 у
каждого события своя папка. Если сообщения прошлых событий нужны, залейте их вручную или
оставьте старую версию работать на отдельном порту.
